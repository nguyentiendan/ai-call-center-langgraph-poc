# Engineering decisions

1. **Frontend deviation (user instruction, 2026-10-29):** Spec Section 3/12 names Streamlit. The user explicitly replaced it with Next.js (≥16.3; installed 16.4.3) + nginx. Backend API is unchanged, so no workflow/security behavior differs. The sanitized debug view from Phase 4 is the right-hand panel in the Next.js UI (state/intent/trace, no secrets). No Streamlit code is shipped.
2. **Graph execution model:** One compiled `StateGraph` per app (nodes = YAML states, conditional edges = YAML transitions), `InMemorySaver` checkpointer with `thread_id = conversation_id`. Each HTTP turn invokes the graph once; pause outcomes end the turn with `AWAITING_INPUT`, and the checkpoint resumes the next turn. Billing reads are idempotent and handoff creation uses `handoff:{conversation_id}` as the idempotency key, so replay on resume cannot duplicate tickets or writes.
3. **PIN channel:** PIN is accepted only by `POST /verify`, hashed transiently in `VerificationService.verify`, then discarded (`demo_pin = ""`). It never enters graph state, messages, trace, or the debug endpoint. `/messages` text that looks like a PIN is treated as ordinary text and cannot verify (tested).
4. **Trusted verification conveyance:** On success the API layer — not the client — calls `TrustedBindings.bind(conversation_id, customer_id)`. `BillingService.get_billing` reads that server-side binding on every call and rejects mismatched/absent bindings. There is no `verified` field in any request schema, so a client cannot forge it.
5. **Security invariants in Python, routing in YAML:** YAML controls transitions/outcomes; Python hard-caps attempts (≤3), clarifications, retries, and refuses a workflow whose `get_billing` state lacks `requires_verified_identity: true`.
6. **Classifier/model:** `FakeModel` is the deterministic offline default. `OpenAIModel` is constructed only with `MODEL_PROVIDER=openai` + `OPENAI_API_KEY`; `/health` reports the active model name honestly. Confidence < 0.75 routes to `unknown`.
7. **Grounding:** Every `円` amount in a generated reply is checked against billing facts; on mismatch the deterministic grounded template replaces the reply (proven with `EvilFakeModel`).
8. **Single process:** In-memory checkpoint/bindings/tickets are demo-only and require one backend process (documented limitation; Postgres checkpointer is Phase 5, out of scope).
9. **Text-first:** No voice, STT/TTS, CTI, AWS, RAG, payment, or real KYC — per spec Sections 1/12 and the user's instruction.
